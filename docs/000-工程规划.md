# aosp-node-bridge（`node-bridge` + `node-runtime`）— 工程规划

> **一句话**：把**真正的 Node.js 运行时**（不是 WebView 里的 JS 引擎、不是云函数、不是 Termux/Magisk 装出来的系统 `node`）以
> `JNI 引导 + dlopen + node::Start` 的形态嵌进 **Android 应用自己的进程**，拆成**两个可发布到 Maven 的 AAR**：
> 一个装接口与加载器（`node-bridge`），一个装引擎（`node-runtime`）。
>
> 它是 [`ohos-node-bridge`](https://github.com/fellow99/ohos-node-bridge) 的 **Android 同构实现**：
> 对标其能力（进程内 Node + 宿主能力桥 + 载荷 + 观测），也**对标其结构**（`node-runtime` 装引擎 / `node-bridge` 装接口）。
> 它不是应用，而是**应用里的 Node.js 脚本环境**，面向多个 Android 工程复用。

## 1. 项目概述

### 1.1 一句话定义

`aosp-node-bridge` 是一个 **Kotlin 库 + JNI 引导件 + 运行时自建链**：它把 Node.js（`libnode.so`）以
`dlopen` + `node::Start` 的方式在**宿主应用自己的进程里**拉起，跑在一条**独立的 detached 线程**上，
并把「启动 / 观测 / 载荷 / 环境 / 宿主能力 / 关停」六件事收敛成一套 Kotlin API 与一套 Node 侧契约，
让应用开发者**不必触碰** C++、`System.loadLibrary` 顺序、SELinux、`targetSdk` 分域与线程模型。

### 1.2 关键结论速览

| 维度 | 结论 | 出处 |
|---|---|---|
| 可行性 | **可行**：上游 Node 自带 Android 构建开关（`android-configure`），`nodejs-mobile` 已用 `libnode.so + JNI + 后台线程`产出生产形态 | ✅ §4.6 / 🔶 §2.3 |
| 运行时形态 | **进程内 `dlopen` + `node::Start`**（路线 A）；`android:process=":node"` 作为**可选加固**（路线 B） | §4.9 |
| 加载方式 | Android 比 OHOS 简单：`System.loadLibrary("node")` 先加载，再 `dlsym("_ZN4node5StartEiPPc")`；**裸名与绝对路径都可用** | §5.10 ① |
| JIT | **本工程最大未知（P0-1）**：`targetSdk ≥ 29` 的 W^X/`execmem` 策略是唯一可能封死 V8 JIT 的地方；`nodejs-mobile` 只对 **iOS** 才加 `--jitless` | ⚠️ §4.5 |
| WASM | 与 JIT 绑定：`--jitless` ⇒ `WebAssembly` 全废（OHOS 已实测 9× 降速 + `fetch` 失败） | 🔶 ohos §4.7 |
| 载荷 | **OHOS 的「`resfile` 只读直读」不可平移**：Android `assets/` **不是文件系统路径** ⇒ 必须首启解包到 `filesDir`（或走 fd/SEA 两条备选） | ⚠️ §5.5 |
| 宿主能力桥 | **主传输 = JNI 推送**（C++ addon → 槽位表 → Kotlin `Handler`），**不需要** OHOS 那套 `napi_threadsafe_function` 绕路；文件邮箱仅作降级 | §5.4 |
| 后台常驻 | **Android 能做**（前台服务 + `foregroundServiceType`），OHOS 封死 ⇒ **能力增量** | §4.4 |
| 崩溃后重启 | 进程内不可；`:node` 独立进程**可重启** ⇒ **能力增量** | §5.2 |
| 分发 | Maven 双 AAR：`node-bridge`（自身 semver）+ `node-runtime`（**版本 = Node 版本**）；靠 `dlopen`+`dlsym` **运行期符号契约**咬合，换 Node 版本不必重编主包 | §7.5 |
| 体积（库侧增量） | `libnode.so` ≈ **100–130 MiB**（⬜ 实测；OHOS 24.2.0 arm64 为 120.9 MiB），AAR 压后 ≈ 35–45 MiB | ⬜ §5.9 / 附录 C |
| 原生模块移植量 | **0**（库侧）：`--expose-internals` + 纯 JS 桩可替代 `require-builtin`；addon 另需 `NEEDED libnode.so`（已由 nodejs-mobile 的 gyp 证明） | 🔶 §4.7 |

## 2. 背景与问题陈述

### 2.1 动机：Android 上「进程内 Node」到底卡在哪

Android 从第一天起就有「在 App 里跑 Node」的实现（`nodejs-mobile`，2017 起），它证明了三件事：

1. `libnode.so` 可以作为共享库被 App 的 JNI 代码 `dlopen` 并调用 `node::Start`（✅ 上游源码结构，🔶 生产应用在使用）；
2. Node 必须跑在**自己的后台线程**（它自带 libuv 事件循环），UI 通过 IPC/HTTP 与它通信 ——
   `doc_mobile/FAQ.md:45-49` 原文：「**Can I run Node.js code in a WebView? No.** … The supported usage scenario is that
   nodejs-mobile runs in a background thread and the UI (in this case a WebView) must use a communication mechanism」；
3. 它是一个**引擎**，不是**库**：没有状态机、没有 loader 版本解耦、没有载荷管理、没有宿主能力桥、没有观测面、
   只有一个「把 `String[]` 拷成连续内存再调 `node::Start`」的 JNI 壳（`tools/mobile-test/android/.../native-lib.cpp:35-108`）。

⇒ 本工程的定位就是补上第 3 条：**把「能跑」变成「可复用、可观测、可发布、可升级」**，且结构上与 OHOS 版对齐。
这与 OHOS 版当年把 `electerm-harmony` 的形态提炼成库是同一条逻辑（🔶 ohos §2.2）。

### 2.2 已有方案盘点与取舍

| 方案 | 形态 | 为什么不用它作主线 |
|---|---|---|
| `nodejs-mobile`（AAR + cordova/RN 插件） | 18.20.4 的 `libnode.so` + 插件壳 | ① **18.x 已 EOL**（2025-04 停止维护），与「Node 24 对标」冲突；② 插件壳把载荷/桥/观测散落在插件层，无对等契约；③ 无版本解耦（引擎与壳同包）。**登记为回退路线**（§4.9 F） |
| Magisk `node_on_android`（`d:\GitHub\android\node`） | root 把官方 `node` 二进制挂进 `/system` | 需 root/remount（`system/etc/mkshrc.d/node_on_android.d.sh:6-10`）、开机服务（`common/service.sh`），**普通 App 完全用不上**。它证明的是「Android 上 Node 能跑」，用的是 **PIE 可执行**（`file` 显示 `interpreter /system/bin/linker64`），**不是** `--shared` 库 |
| WebView 内 JS / QuickJS / Hermes | 另起 JS 引擎 | 不是 Node：无 `node:fs`/`node:http`/原生模块生态；改造上游工程量 = 重写 |
| Termux / 用户装 Node | 外部进程 | 需用户装 App、无沙箱权限、无法上架 |
| 远端 Node（云函数/局域网） | 网络依赖 | 违背「本地、离线可用」；首个消费方要求端上 |
| 子进程 `execve` 自带 node 二进制 | 独立进程 | Play 政策 + `targetSdk` 收紧 + App 数据目录 `noexec` 风险 + 体积翻倍（§4.4） |

## 3. 目标与原则

### 3.1 目标

1. **能起**：宿主在自己的进程里把 Node 拉起来；`process.platform === 'android'`、`process.arch === 'arm64'`、`process.version` 命中版本矩阵。
2. **能观测**：Kotlin 侧拿到状态机 + 结构化日志 + 上一次崩溃记录；一条命令验「服务真的在端上跑」。
3. **能承载**：一份载荷（`assets` 里的 `tar.gz`，首启解包后的目录也算）+ 入口脚本 + 环境变量 + argv，能跑起真实服务端。
4. **能对话**：Node 侧用一个稳定 API 调回 Kotlin 侧宿主能力；未注册即结构化报错，绝不静默。
5. **能上架**：无动态下载可执行代码、无绕过平台控制、许可齐备、体积可控（§9.5）。
6. **能发布**：双 AAR 上线 Maven，接入方式可文档化、可复现。
7. **失败可见**：任何一步失败都在 UI 上留下**可截图/可断言**的文字，而不是白屏。

### 3.2 设计原则

| 原则 | 展开 |
|---|---|
| **库/壳分离** | 库只负责「在进程内跑 Node」；一切应用语义（Activity/WebView/鉴权/pi）留在消费方。API 面越小越稳 |
| **不隐藏平台真相** | 能力缺口（`spawn` 受限、`process.exit` 语义、`os.cpus()` 不可靠）**如实上报为能力标志**，绝不静默降级 |
| **让最终使用者去读** | 凡「写入成功」的判据，一律改为「最终使用者读一遍」（Node 写、Node 读回） |
| **启动参数不可事后修改** | `execArgv` 只能在 `node::Start` 之前定；库把它做成显式选项 + 立即冻结 |
| **单例与不可重启** | 进程内只有一个实例；「重启」在进程内语义上不可实现 ⇒ 暴露成显式失败态，或换 `:node` 进程 |
| **诊断优先于修码** | 先建观测通道（logcat / 文件日志 / `adb forward` + curl / `/facts`），再动代码 |
| **零上游补丁优先** | 能用现成机制（`configure` 开关、`LDFLAGS`、`NDK` 变量）就不打补丁；补丁必须**幂等、可反向、带 commit 出处** |
| **可复现供应链** | 自建产物必须能从「tag + NDK 版本 + 命令」一条链复现；锁文件记录 SHA-256 与门禁结果 |

### 4.2 A 类：可依赖（有源码/产物证据）

① **`--shared` 出 `libnode.so`** —— 上游 `configure.py` 已有 `node_shared` 变量与 android 的 `shlib_suffix='so'` 分支；
`nodejs-mobile` 用它出了 4 个 ABI 的 `libnode.so`（`tools/android_build.sh:43-49`）。

② **`node::Start(argc, argv)` 是唯一需要的入口** —— `src/node.h:318`；`argv` 必须是**连续内存**（`native-lib.cpp:42,49-65`
的注释：「Node's libuv requires all arguments being on contiguous memory」），且 **`argc` 不含尾部 `nullptr` 哨兵**
（OHOS 硬约束 ③ 已实测：算进去 ⇒ 5 ms 内段错误）。

③ **Node 自带 libuv 事件循环，必须跑在专用线程** —— `src/api/embed_helpers.cc:19-46` 的 `SpinEventLoop` 直到 loop 死；
`node::Start` **直到进程结束才返回**（或 loop 自然结束）。⇒ 宿主侧**绝不 join**。

④ **JNI 壳极薄** —— Java `Thread` → `native startNode(String[])` → 拷连续内存 → `node::Start`。本工程只需在它上面
加状态机、stdio 重建、崩溃 handler、dlopen 候选链与槽位表。

⑤ **AAR 携带原生库是官方语义** —— AAR 的 `jni/<abi>/*.so` 由 AGP 合并进 APK 的 `lib/<abi>/`；`extractNativeLibs=false` 时
直接从 APK 映射（16 KB 对齐由 AGP `android.bundle.enableUncompressedNativeLibs` 保证）。

⑥ **`System.loadLibrary` 负责一切加载细节** —— 命名空间、APK 内映射、`JNI_OnLoad`。⇒ 引导件**先调 `System.loadLibrary("node")`
把引擎装进本进程**，再 `dlsym(RTLD_DEFAULT, "_ZN4node5StartEiPPc")`；这条路径绕开了 OHOS「只认裸名/绝对路径失配」的坑。

⑦ **16 KB 页** —— `-Wl,-z,max-page-size=16384`（nodejs-mobile commit `d9552e0e01`），NDK r27+ 默认已 16 KB 对齐。

### 4.5 ⚠️ 专项一：JIT ↔ W^X ↔ `execmem`（本工程最关键的未知）

**已知事实（可复核）**

1. V8 的代码页走 **匿名映射 + `PROT_READ|PROT_WRITE|PROT_EXEC`**：
   `nodejs-mobile:deps/v8/src/base/platform/platform-posix.cc:127-152`（`kReadWriteExecute → PROT_READ|PROT_WRITE|PROT_EXEC`，
   `GetFlagsForMemoryPermission` 用 `MAP_ANONYMOUS`）。
2. Android 10（API 29）起对**应用域**做 W^X：`targetSdk ≥ 29` 的应用不再具备 `execmem` 能力，匿名可执行映射
   被 SELinux 拒绝（表现为 `mprotect` 返回 `EACCES`，或 V8 侧 `CHECK` 失败/`SIGSEGV`）。⚠️ 本条为**平台策略陈述**，
   本工程未在目标设备复核 ⇒ 归入 P0-1。
3. 平台自己（ART）的 JIT 走的是**文件后备（memfd/JIT-cache）双视图**：同一份文件分别映射成 RW 与 RX，
   从不出现「同一映射既可写又可执行」。
4. `nodejs-mobile` 只在 **iOS** 加 `--jitless`（`tools/ios_framework_prepare.sh:71-73`），Android 不加
   ⇒ 反证「Android 上 JIT 可用」。
5. 上游 Node 有官方 Android 构建开关（`android-configure`），但「unsupported」。

**⇒ 三条路线与判定矩阵（P0-1 就是为它们设的）**

| 组 | 组合 | 判据（可证伪） |
|---|---|---|
| ① | 默认（JIT），`targetSdk 36` | Node 起得来、`WebAssembly.validate` 为 `true`、热循环 < 50 ms ⇒ **成立，主线走「路线 J（JIT）」** |
| ② | 默认（JIT），`targetSdk 28`（对照实验，仅诊断用） | ①失败而②成功 ⇒ **锁定根因是 W^X/`execmem`**，需要 ③ 或 ④ |
| ③ | `--jitless`（「路线 I（解释器）」） | `WebAssembly` 未定义、热循环 ~9× 慢（OHOS 实测 299 ms/5 轮 vs 6–9 ms/2e6）⇒ **只能跑「零运行期 WASM」载荷** |
| ④ | 代码页改「文件后备双视图」 | 需 interpose `mmap/mprotect` 或改 V8；**性能与合规双风险**，默认**不投入**（与 OHOS 路线 J′ 同性质：不得进上架包） |

> **为什么这条是本工程最重要的一条判断**：首个消费方的载荷（Next 的 WASM SWC、undici 的 llhttp WASM）**依赖 JIT**。
> 若 ① 不成立，产品能力会**直接降一档**（要么改载荷为「零运行期 WASM」，要么换设备/换系统版本策略）。
> 因此 **P0-1 必须在写任何业务代码之前出结论**，且必须三组都测 —— 不接受「先跑起来再说」。

### 4.6 ⚠️ 专项二：`libnode.so` 的供给（自建 vs 沿用）

| 路线 | 做法 | 判断 |
|---|---|---|
| **自建（选定）** | `nodejs/node@v24.x` + NDK + `./android-configure <ndk> 24 arm64` **补 `--shared`**（可再补 `--with-intl=full-icu`）+ `LDFLAGS=-Wl,-z,max-page-size=16384` → `out/Release/lib.target/libnode.so` | ✅ **用户已定档**。理由：18.x EOL、供应链自控、与 OHOS 版共用版本号与配方 |
| 沿用 nodejs-mobile 18.20.4 | 直接取 `out_android/arm64-v8a/libnode.so` | ⏸ **回退**（仅在自建卡死且需要在 2 周内出货时启用）；EOL 风险显式登记（R2） |
| 上游官方 Android 预编译 | 不存在（unsupported） | ❌ |
| OHOS 的 `libnode-arm64.so`（openharmony） | 来自 `electerm/ohos-node-shared` | ❌ 目标 OS 不同（TLS/ABI/linker 语义），不可混用 |

**自建的四个必须自己补的东西**（上游 `android_configure.py` 不含）：

1. `--shared`（否则只出 `node` 可执行文件）；
2. `LDFLAGS=-Wl,-z,max-page-size=16384`（16 KB 页；Play 要求）；
3. **V8 trap-handler patch**（`android-patches/trap-handler.h.patch`：把 `V8_TRAP_HANDLER_SUPPORTED` 定为 `false`，
   对应上游 issue `nodejs/node#36287`）—— ⬜ 需在 Node 24 上复核是否仍必需（V8 12+ 该文件已重构）；
4. `-soname libnode.so`（保证 addon 的 `DT_NEEDED` 能命中，§4.7）。

> **纪律**：这四条必须写进 `tools/build-runtime.sh`（或 `.mjs`）**而不是「我本机这么跑的」**，且每条带来源出处。
> 上游 `BUILDING.md:805` 已明说 unsupported ⇒ **我们的构建脚本是唯一事实源**，能在干净 Linux 容器里一条命令复现。

### 4.7 ⚠️ 专项三：`libc++` 与 addon 的 `NEEDED` 契约（Android 特有）

OHOS 版踩过两个坑（🔶 ohos §9.1 R18 / 能力矩阵 #11）：主桥 `.so` 不能同时服务 ArkTS 的 NAPI 与 Node 的 NAPI env（两套实现），
且专用 addon 因为 `DT_NEEDED` 不含 libnode 而 `symbol not found`。Android 侧的对应结论：

| 项 | Android 事实 | 设计动作 |
|---|---|---|
| 两套 NAPI 实现？ | **没有**：Android 侧是 JNI，不是 NAPI。Node 侧只有一个 NAPI 实现（`libnode.so`） | 不必拆分「每 env 一个 .so」，但**仍要拆两个 .so**：`libnode_bridge.so`（JNI）与 `libnode_host_client.so`（NAPI addon），理由见下 |
| addon 符号解析 | 必须 `DT_NEEDED libnode.so`（`nodejs-mobile:common.gypi:516-533` 明文） | addon 的 CMake 集成里加 `-l:libnode.so` + `-Wl,--no-as-needed`；或 lint 检查 `readelf -d` 含 `NEEDED libnode.so` |
| 为什么还要拆两个 `.so` | JNI 侧的 `libnode_bridge.so` 若同时导出 `napi_register_module_v1`，它会被 `System.loadLibrary` 加载（`RTLD_LOCAL` 语义），Node 侧 `require` 时不会二次注册；更重要的是**它不链接 `napi_*`**（靠 `RTLD_GLOBAL` 解析）这一点必须与其 JNI 导出解耦，便于分别验证 | 两个 `.so` + 一条符号契约：addon 只 `dlsym(RTLD_DEFAULT,"anb_host_call")` |
| `libc++` | Node gyp 未加 `-static-libstdc++` ⇒ 大概率 `NEEDED libc++_shared.so`（⬜ P0-5） | **首选 `-static-libstdc++` 自建**（`LDFLAGS` 追加），把 `libc++` 固化进 `libnode.so`，避免与宿主 App 的同名库冲突；若不可行 ⇒ `node-runtime` AAR 里带 `libc++_shared.so` 并在 README 声明「本库供给，勿重复」 |
| `SONAME` | 必须是 `libnode.so`（不能是 `libnode.so.<modules>`） | 构建脚本显式 `-Wl,-soname,libnode.so`，并做成 ELF 门禁之一 |

### 4.8 Android 与 HarmonyOS 的 12 条本质差异（**决定哪些结论不能平移**）

| # | 维度 | HarmonyOS（OHOS 工程实测） | Android（本工程） | 对设计的影响 |
|---|---|---|---|---|
| 1 | 只读载荷路径 | `resources/resfile/` 是**真路径**，可直读 | `assets/` **不是**路径 | 载荷**必须解包**（§5.5） |
| 2 | 原生库加载 | 只认裸名 `libnode.so`；绝对路径全失败 | `System.loadLibrary` 最稳；裸名亦可用 | 加载顺序改为「先 `loadLibrary` 再 `dlsym`」 |
| 3 | JIT 门槛 | 受限 ACL（刚性、需申报） | **无 ACL**，风险在 `targetSdk` 的 W^X | 风险面从「审批流程」变「平台策略」 |
| 4 | 后台常驻 | 封死（`9800005`） | 前台服务可行 | **能力增量**：可做「常驻 agent」 |
| 5 | 崩溃后恢复 | 不可（进程内） | 进程内不可，`:node` 进程可 | **能力增量**（可选形态） |
| 6 | 子进程 | 两份互斥证据（EACCES vs 事件不送达） | FAQ 明说不支持；`/system/bin/sh` 存在 | 一律**不依赖** `spawn` |
| 7 | 宿主能力面 | `@ohos.*` + `callArkTSFunction`（≤3 参原始类型） | **JNI 直调 Java**：`Context`/`PackageManager`/`Intent`/`ActivityResult` | 桥的能力清单更宽（§5.4） |
| 8 | UI 线程 | `dlopen` 在 UI 线程 ⇒ `APP_INPUT_BLOCK` | 主线程做重活 ⇒ **ANR（5 s/10 s/20 s）** | 同样必须 detached 线程 |
| 9 | 打包压缩 | `compressNativeLibs`（module 级） | `useLegacyPackaging` / `extractNativeLibs` / zip 对齐 | 核对产物要看 APK，不看磁盘（同纪律） |
| 10 | 分发与体积 | ohpm HAR；单包 41 MB 可用 | Maven AAR；**Play AAB 有下载体积上限** | 载荷超大时要考虑 Play Asset Delivery |
| 11 | 调试 | `hdc fport` + DevTools | `adb forward` + `chrome://inspect` | 语义等价 |
| 12 | 观测 | hilog（应用侧 INFO 常不入缓冲） | `logcat`（`__android_log_write`）+ tombstone | 双通道：logcat + 文件 |

### 4.9 候选路线与取舍

| 路线 | 形态 | 判断 |
|---|---|---|
| **A：进程内 `dlopen` + `node::Start`**（选定主线） | 库在宿主进程跑 Node，WebView 加载 `127.0.0.1` | ✅ **选定**。与 OHOS 同构；JNI 壳最薄；零 IPC 的 HTTP 数据面 |
| **B：`:node` 独立进程**（选定为**可选加固**） | `AndroidManifest` 声明 `android:process=":node"` 的 `Service` | ✅ **保留**。唯一能「重启 Node」的形态；代价是 IPC（`Binder`/`LocalSocket`）与内存翻倍。**不设为默认**（默认仍要与消费方共用 `Context` 能力） |
| C：子进程 exec 自带 node 二进制 | 打包 `libnode-exec.so` 改名技巧 + `execve` | ❌ 不选：Play 政策风险、`noexec` 趋势、体积翻倍、FAQ 明说权限问题 |
| D：WebView 内 JS 引擎 | QuickJS/Hermes/JSC in WebView | ❌ 不选：不是 Node（无 `fs`/`http`/原生模块） |
| E：远端/云端 Node | 网络依赖 | ❌ 不选：违背本地离线 |
| F：直接用 `nodejs-mobile` AAR | 18.20.4 现成产物 | ⏸ **回退**（登记，不投入）。触发条件：P0-3 自建链在 2 周内出不了可用产物 |

**选 A 的四条理由**：① 与 OHOS 版同构 ⇒ 文档、契约、模块编号、踩坑清单可复用；② JNI 壳比 NAPI 更薄（无两套 NAPI 实现问题）；
③ 数据面零 IPC（同进程 + 同源 HTTP）；④ 消费方零 C++。

## 5. 核心架构方案

### 5.1 分层架构

```
┌─ 宿主应用（消费方） ────────────────────────────────────────────────────────────┐
│  Activity + WebView + 加载/错误页 + 目录选择器 + 外链 + 通知 + 前台服务            │
│  Node 侧启动脚本：环境装配 → 载荷就绪 → 起本地服务 → 就绪判定                      │
└──────────────┬────────────────────────────────────────────────────────────────┘
               │ Kotlin API（io.github.fellow99:node-bridge）
┌──────────────┴────────────────────────────────────────────────────────────────┐
│  libnode_bridge.so（JNI 引导件，随 AAR 编译）                                     │
│   ├─ JNI 导出（**只 6 个**）：start / isRunning / stage / lastError / pollSlots…  │
│   ├─ 宿主能力桥：槽位表（mutex+condvar）+ 回调到 Kotlin Handler                   │
│   ├─ detached bootstrap 线程（32 MB 栈）：dlopen → dlsym → node::Start           │
│   ├─ stdio 重建：fd0←/dev/null、fd1/2←各自 pipe + 独立 reader 线程                │
│   ├─ io_uring 防御：`UV_USE_IO_URING=0`（Android 由 seccomp 返回错误，不 trap）    │
│   └─ 崩溃 handler → logcat + last-crash.json（单次 write）                        │
└──────────────┬────────────────────────────────────────────────────────────────┘
               │ dlopen（先 System.loadLibrary("node")，再 dlsym RTLD_DEFAULT）
┌──────────────┴────────────────────────────────────────────────────────────────┐
│  APK lib/arm64-v8a/：libnode.so（≈100–130 MiB）+ libnode_bridge.so               │
│                      + libnode_host_client.so（NAPI addon，NEEDED libnode.so）   │
│  assets/：payload.tar.gz（`noCompress` 声明）+ bootstrap.js / selfcheck.js       │
└──────────────┬────────────────────────────────────────────────────────────────┘
               │ 首启解包到可写目录 <filesDir>/node-bridge/{payload,tmp}
┌──────────────┴────────────────────────────────────────────────────────────────┐
│  Node 运行时（libuv 事件循环，自己的 pthread）                                    │
│   bootstrap.js：解包（幂等 marker）→ 入口解析（CJS/ESM）→ require → 应用逻辑       │
│   宿主桥：require('@aosp-node-bridge/host').invoke('perm.check', …)           │
└────────────────────────────────────────────────────────────────────────────────┘
```

**一条关键边界**：库**不参与**渲染。WebView、加载页、错误页、Cookie、导航围栏都是消费方的事；库只保证「本地服务在端上跑着」。

### 5.2 进程与线程模型

| 项 | 设计 | 依据 |
|---|---|---|
| 进程 | 默认**与宿主同进程**（`pid` = App pid）；`:node` 为可选（§4.9 B） | 路线 A |
| 启动线程 | `std::thread(...).detach()` 一条专用 pthread（**32 MB 栈**）做 `dlopen`+`dlsym`+`node::Start` | 主线程会 ANR；OHOS 同构（32 MB 栈是为 V8 递归与 `--stack-size`） |
| 与 Kotlin 线程的关系 | **完全解耦**：Kotlin 只做「投递启动参数 + 读状态 + 读日志」，绝不 join | `node::Start` 直到进程结束才返回 |
| 单例 | 进程内单例 `NodeRuntime.getInstance(ctx)`；`start()` 只允许一次；二次调用返回 `StartResult.AlreadyStarted` 并保留首次原因 | `InitializeOncePerProcess` |
| 状态机 | `idle → starting → running → (failed) → stopping → stopped` + **`exited`**（`node::Start` 正常返回） | 失败可见；`exited` 是 Android 特有（Node 侧 `process.exit`/loop 结束） |
| 失败后的恢复 | **不假装恢复**：`failed` 后只允许「读日志 / 读上次崩溃 / 提示重启 App」；`:node` 形态可以重启**进程** | 原则「单例与不可重启」 |
| 关停 | `shutdown(reason)` = 在 Node 线程执行应用注册的 `onShutdown` 钩子（如 `server.close()`）+ 窗口期等待；**真正的停止只能是进程退出** | 同 OHOS §5.2 |
| 载荷解包 | 在 **Kotlin 侧**做（`AssetManager` 只有 Java/Kotlin 侧能高效流式读），解包完再启动 Node | 与 OHOS「谁写谁读」不同：Android 同 uid 同目录无该坑（§4.8 #1） |
| 就绪判定 | 库**不猜**：消费方探活成功调 `markRunning()`，超时/读到崩溃调 `markFailed(reason)` | 同 OHOS D8（库不认识端口） |

**为什么 `exited` 很重要**：Android 上 `process.exit(0)` 不会杀 App，`node::Start` 返回后该线程结束、运行时**永久死亡**
（再次 `start()` 必失败）。若不显式建模，消费方会看到「状态永远 running 但服务不响应」这种最难查的故障。

### 5.3 Kotlin 对外 API（草案）

```kotlin
// io.github.fellow99.nodebridge —— 唯一出口：NodeBridge（barrel）

sealed interface NodeState {
  data object Idle : NodeState
  data object Starting : NodeState
  data class Running(val pid: Int, val nodeVersion: String) : NodeState
  data class Failed(val stage: String, val message: String, val signal: Int?) : NodeState
  data object Stopping : NodeState
  data object Stopped : NodeState          // shutdown 后 / 进程结束
  data class Exited(val code: Int) : NodeState  // node::Start 正常返回
}

enum class ProcessMode { IN_PROCESS, DEDICATED_PROCESS }   // 后者需消费方声明 :node Service（§5.2）

data class NodeRuntimeOptions(
  val entry: String,                      // 相对 payloadRoot 或绝对路径
  val payloadRoot: String? = null,        // 默认 <filesDir>/node-bridge/payload
  val archiveAsset: String? = null,       // assets 内 tar.gz；给出即首启解包（幂等）
  val archiveSha256: String? = null,      // 幂等 marker 的判据
  val argv: List<String> = emptyList(),
  val execArgv: List<String> = emptyList(),   // 启动即冻结（不可事后 push）；注意 `--no-verify-heap` 在 Node 18 不存在（传了 ⇒ node::Start 立即返回 UV_EBADF/9）
  val env: Map<String, String> = emptyMap(),
  val cwd: String? = null,                // 默认 payloadRoot
  val capBytes: Long = 8L shl 20,         // 单次 JSON 载荷上限（8 MiB）
  val logRingSize: Int = 500,
  val jitless: Boolean = false,           // 诊断专用；用了就等于关掉 WASM（§4.5）
  val processMode: ProcessMode = ProcessMode.IN_PROCESS,
)

data class StartResult(val ok: Boolean, val code: Int, val state: NodeState, val message: String?)
data class NodeLogEntry(val at: Long, val stream: String /* stdout|stderr|system */, val text: String)
data class CrashRecord(val at: Long, val stage: String, val signal: Int?, val hint: String?, val logTail: List<String>)

class NodeRuntime private constructor(ctx: Context) {
  companion object { fun getInstance(ctx: Context): NodeRuntime }

  val state: StateFlow<NodeState>            // 不再要求消费方 100ms 轮询
  val pid: Int                               // = 宿主 pid（不是子进程）
  val host: NodeHostBridge                   // 宿主能力桥

  fun start(opts: NodeRuntimeOptions): StartResult          // 投递语义：立即返回
  suspend fun awaitRunning(timeoutMs: Long = 60_000): NodeState
  fun markRunning()                          // 消费方探活成功后调用
  fun markFailed(reason: String)
  fun logs(): List<NodeLogEntry>              // 有界环（默认 500 行）+ 丢弃计数
  fun lastCrash(): CrashRecord?               // 上次运行留下的崩溃记录
  fun shutdown(reason: String): Boolean       // 触发 Node 侧 onShutdown 钩子；返回「是否投递成功」
}

interface NodeHostBridge {
  /** 注册宿主能力；handler 在主线程被调用，入参/出参都是 JSON 字符串 */
  fun register(name: String, handler: (payloadJson: String) -> String)
  /** 异步版本（如文件选择器）：完成后 resume */
  fun registerAsync(name: String, handler: (payloadJson: String, done: (String) -> Unit) -> Unit)
  fun unregister(name: String)
  fun names(): List<String>                   // 供日志与自检
}
```

> **与 OHOS 的差异（刻意为之）**：① `state` 用 `StateFlow` 推送（Android 有真实的 `Looper`，不需要轮询）；
> ② `markRunning()/markFailed()` 显式暴露（同 OHOS D8 的「库不猜就绪」）；③ `exited` 态；④ `processMode` 预留。

### 5.4 Node 侧 host API 与桥协议

Node 侧（由 `libnode_host_client.so` 暴露的内置模块，无需 npm 安装）：

```js
const host = require('@aosp-node-bridge/host');

const facts  = await host.invoke('runtime.facts');            // { node, platform, arch, execArgv, state, pids }
const picked = await host.invoke('fs.pickFolder', { title: '选择目录' });
host.handle('shutdown', () => new Promise(r => server.close(r)));  // 注册 Node 侧钩子
// 未注册的名字 ⇒ reject({ ok:false, error:'unregistered', name })
```

**协议（语言中立、可序列化）**

| 项 | 设计 | 依据 |
|---|---|---|
| 载体 | **JSON 字符串**（不是值对象） | 不受参数个数/类型限制；跨语言无歧义 |
| 槽位 | `id`（int64）+ `name`（≤128 B）+ `args`（≤8 KiB）+ `result`（≤64 KiB） | 有界；超限即报错而非截断 |
| 方向 1（Node → Kotlin） | Node 线程 `host.invoke` → 写入槽位 → **JNI 调用 Kotlin 静态方法** `NodeBridgeNative.onHostRequest(json)` → Kotlin 主线程执行 handler → `nativeCompleteRequest(id, result)` → Node 线程被唤醒 | Node 线程**不阻塞在 Kotlin 上超过超时**（默认 10 s） |
| 方向 2（Kotlin → Node） | **只有两条**：`start()` 的启动参数、`shutdown()`。不提供「Kotlin 调 Node 函数」的通用入口 | API 面小；应用语义走 HTTP/文件 |
| JNI 线程 | `JNI_OnLoad` 缓存 `JavaVM*`；Node 线程首次用时 `AttachCurrentThread`（`thread_local` 缓存 `JNIEnv*`；detach 线程退出时做） | 避免 `JNI DETACHED_THREAD_VIOLATION` |
| 能力清单（v1） | `runtime.facts` · `perm.check` · `perm.openAppInfo` · `fs.pickFiles` / `fs.pickFolder`（`ACTION_OPEN_DOCUMENT`/`ACTION_OPEN_DOCUMENT_TREE`）· `shell.openExternal` · `notify.show` · `log.i` · `device.info` | 与 OHOS 的清单逐项对齐（🔶 ohos §5.4） |
| 失败语义 | 未注册 → 结构化 reject；超时 → `{ ok:false, error:'timeout' }`；handler 抛异常 → `{ ok:false, error:'handler-threw', message }` | 绝不静默返回空（OHOS 的反面教材：未注册能力把整个应用打崩） |
| 降级通道 | 文件邮箱（`<filesDir>/node-bridge/host-mailbox/{*.req,*.ok,*.fail}`，100 ms 轮询）**仅用于**「JNI 路径不可用」的诊断与非 Android 单测 | 🔶 OHOS 现状做法，保留为兜底 |

> **为什么 Android 不需要 `napi_threadsafe_function`**：那是 ArkTS 侧的概念；Android 侧只有 JNI + `Handler`，
> 槽位表 + `AttachCurrentThread` 已经覆盖同样的语义，且**少一层跨语言队列**。

### 5.5 载荷分发与入口解析

| 决策 | 内容 | 依据 |
|---|---|---|
| 形态（主线） | **`assets/payload.tar.gz`（`noCompress` 声明）+ 首启解包到 `<filesDir>/node-bridge/payload`** | `assets` 不是路径（§4.8 #1）；`noCompress` 使 `openFd` 与快速拷贝可行 |
| 幂等 | 目标目录 + `.ready-<sha256 前 12 位>` marker；命中即跳过；解包先落 `.tmp-<pid>` 再 `rename` | 半包损坏可自愈；`rename` 同分区原子 |
| 谁解包 | **Kotlin**（`ZipInputStream`/`TarArchiveInputStream` 流式写） | `AssetManager` 侧最省内存；Android 无 OHOS「谁写谁读」的坑 |
| 解包上限 | 单文件 ≤ 512 MiB、总大小校验、路径穿越校验（拒绝 `..`/绝对路径/符号链接） | 安全；防 zip-slip |
| 入口 | `entry` 解析为**绝对路径**后 `require()`；`ERR_REQUIRE_ESM`/`ERR_REQUIRE_ASYNC_MODULE` 退 `import(pathToFileURL(...))` | 同 OHOS §5.5（CJS/ESM 混用） |
| `cwd` | 默认 `payloadRoot`，由库 `process.chdir` | 上游常以 `resolve(process.cwd(),'package.json')` 定位 |
| 备选 D2（省一次拷贝） | `assets` 内单个**未压缩**归档 + `AssetFileDescriptor.getStartOffset/getLength` + `dup()` → 把 `/proc/self/fd/<n>` 传给 Node（必要时先 `lseek`），Node 自己读 | 需 P0-6 顺带验证；**仅当**首启解包耗时不可接受时启用 |
| 备选 D3（免解包） | Node 24 的 **snapshot blob**（`--build-snapshot` 产物）承载「单文件 JS 包」 | ⬜ 评估项：适合小载荷/单文件 bundle；不适合完整 `node_modules` |
| 大载荷 | 若载荷 > 100 MB：走 Play Asset Delivery 或按目录分卷（`payload-core` / `payload-app`），避免单文件超限 | 与 OHOS「目录分卷」建议同构 |

**只读直读在 Android 上为什么不行（写清楚，避免后来者踩）**：`resfile`（OHOS）是 HAP 解包后的真实目录；Android 的
`assets/` 只在 APK zip 内部，`AssetManager` 只提供流与「未压缩时」的 fd，**没有可供 `require` 的目录路径**。
任何「把 assets 当 `/path/to/assets` 拼路径」的写法在不同 ROM/ABI 上都不可靠。

### 5.6 环境契约

| 变量 | 值 | 谁设 | 理由 |
|---|---|---|---|
| `HOME` / `USERPROFILE` | `<filesDir>/node-bridge` | **库** | Android 无 `$HOME`，`os.homedir()` 会抛/返回空 |
| `TMPDIR` / `TMP` / `TEMP` | `<cacheDir>/node-bridge/tmp` | **库** | `/tmp` 不存在（`os.tmpdir()` 默认 `/data/local/tmp`，不可写） |
| `UV_USE_IO_URING` | `0` | **库**（强制，`node::Start` 之前） | Android seccomp 下 `io_uring_setup` 被拒；减少无效探测 |
| `NODE_OPTIONS` | **清空** | **库** | 避免宿主机/构建环境污染 |
| `ANDROID_DATA` / `ANDROID_ROOT` | **不改** | — | 由 zygote 设置，改动有害 |
| `NODE_PATH` | 追加 `<payloadRoot>/node_modules` | 库（可选） | 便于载荷外置依赖（nodejs-mobile 的 JNI 壳也这么做） |
| 应用语义变量 | 由消费方经 `env` 传入（`PI_*`、密码、根目录白名单） | **消费方** | 库不认识应用语义 |
| `LD_LIBRARY_PATH` 等 | **不改** | — | Android linker 命名空间特殊；改动会连带影响宿主 |

### 5.7 日志与崩溃取证

| 通道 | 设计 |
|---|---|
| stdout/stderr | C 侧 `pipe` + `dup2` → 两个**独立 reader 线程**逐行 → 有界日志环（默认 500 行）+ `<filesDir>/node-bridge/node.log` + `__android_log_write`（tag `NODE_BRIDGE`）。**fd0 指向 `/dev/null`** |
| Kotlin 读取 | `logs()` / `node.log` 文件尾；消费方渲染到「开发者/诊断」面板（一张截图胜过十次盲猜） |
| 崩溃记录 | 信号 handler（`SIGSEGV/ILL/BUS/ABRT/FPE/TRAP`）**只**做 `write(2)`，写 `CRASH sig=… si_addr=… pc=… lr=… sp=… stage=…` 整行 + `<filesDir>/node-bridge/last-crash.json`；handler 内**禁止** `printf`/`__android_log_write`（非 async-signal-safe） |
| 系统侧 | 同时保留 system tombstone（`logcat -b crash`、`adb shell dumpsys dropbox`）作为第二证据源 —— 自建 handler **不替代**它 |
| 端到端证书 | 库自带 `selfcheck` 载荷：起 `node:http` 并暴露 `/facts`（`{node, platform, arch, execArgv, hostBridge, state, fsRoundTrip}`），`adb forward tcp:15577 tcp:15577` + `curl` 即证书 |
| 调试通道 | **debug 构建才允许** `--inspect`（`adb forward tcp:9229 tcp:9229` + `chrome://inspect`）；release 必须关闭 |
| 禁止的判据 | 不用 `logcat`「有没有那行」判执行（缓冲与 tag 过滤会骗人）；不用 `VmSize` 判 V8 是否起来；不用「点击看起来生效」判 UI |

### 5.8 运行时的获取、自建与校验

| 项 | 设计 |
|---|---|
| 锁定（唯一事实源） | **`runtime.lock.json`**（入库）：`{active, releases: [{node, abi, size, sha256, soname, needed, builtFrom: {tag, ndk, cmd, patches}, gates, verifiedOn, verifiedDevice}]}`；**二进制不入库**（100 MB+ 超 GitHub 单文件限） |
| 自建流水线 | `tools/build-runtime.sh`：拉 `nodejs/node@v24.x` → 应用 patch → `./android-configure <ndk> 24 arm64`（**补 `--shared`**）→ `make -j` → 产物 `out/Release/lib.target/libnode.so` → `llvm-strip` → 复制到 `runtime-build/libs/arm64-v8a/` |
| 校验（**八项门禁，任一不过即硬失败**） | ① `e_type = ET_DYN`；② `PT_INTERP` 计数 = 0（PIE 直接拒）；③ `e_machine = AArch64`；④ `DT_SONAME = libnode.so`；⑤ `_ZN4node5StartEiPPc` 在 `.dynsym` **已定义并导出**；⑥ SHA-256 与锁文件一致；⑦ 大小一致且版本串存在；⑧ **16 KB 页对齐**（`readelf -lW` 段对齐 ≥ 0x4000） |
| 投放 | `tools/provision.mjs --check` / `--out node-runtime/src/main/jniLibs/arm64-v8a`（幂等）；本地目录优先，可 `--from <归档|url>` |
| 版本要求 | `process.version` 命中矩阵（≥ 22.19 才允许消费 Next 类载荷）；不命中即启动 warn（**不静默**） |
| 供应链纪律 | tag + NDK 版本 + 完整命令 + patch 清单 + 许可清单；每条记录带 `verifiedOn`/`verifiedDevice` |

### 5.9 打包与体积

### 5.10 已证实的落地要点（逐条进实现清单）

| # | 要点 | 为什么（不做会怎样） | 来源 |
|---|---|---|---|
| 1 | 引导件**先** `System.loadLibrary("node")`，**再** `dlsym(RTLD_DEFAULT,"_ZN4node5StartEiPPc")`；`dlopen("libnode.so", RTLD_NOW|RTLD_GLOBAL)` 作为等价路径 | 避免「路径猜错 / 命名空间找不到」；`RTLD_GLOBAL` 让 addon 的 `napi_*` 能解析 | ✅ §4.2 ⑥ + 🔶 ohos D5 |
| 2 | `argv` 连续内存 + **`argc` 不含尾部 `NULL`** | 含哨兵 ⇒ Node 拿到 `NULL` 参数，5 ms 内段错误 | 🔶 ohos 硬约束 ③ |
| 3 | bootstrap 在 **detached pthread（32 MB 栈）** | 主线程 ⇒ ANR；小栈 ⇒ 深递归崩溃 | 🔶 ohos 硬约束（ANR 等价物） |
| 4 | **stdio 必须重建并持续排空**（fd0→`/dev/null`，fd1/2→pipe + reader 线程） | App 进程 fd1/2 指向 `/dev/null`，`console.log` 全丢；不排空 ⇒ 写满 64 KB 后 Node 阻塞 | ⬜ P0-9 + 🔶 ohos R19 |
| 5 | 崩溃 handler 内**只用 `write(2)`**，禁 stdio / `__android_log_write` | 信号上下文里调非信号安全函数 ⇒ 二次崩溃 | 🔶 ohos §5.10 ② |
| 6 | `--expose-internals` 必须出现在**启动参数**里（若载荷走 internal 桩路线） | `internal/modules/*` 全部 `MODULE_NOT_FOUND` | 🔶 ohos 硬约束 ⑤ |
| 7 | addon 必须有 `DT_NEEDED libnode.so` | 否则 `Error relocating …: napi_create_function: symbol not found` | ✅ nodejs-mobile `common.gypi:516-533` |
| 8 | 端口由 Node 侧随机/先探测空闲；宿主必须**单实例** | 端口冲突 ⇒ 未捕获异常 ⇒ 进程 abort（无优雅退出路径） | 🔶 ohos §6.2 ⑰ |
| 9 | 载荷必须自装 `uncaughtException`/`unhandledRejection` 兜底并写**独立日志通道** | 进程内 Node 没有优雅退出路径；默认 stderr 会与组件输出混流 | 🔶 ohos §6.2 ⑱ |
| 10 | `HOME`/`TMPDIR` 由库强制重定向 | Android 无 `$HOME`/`/tmp` | ✅ §5.6 |
| 11 | `execArgv` 一次性冻结 | `process.execArgv` 启动即固定，运行期 push 无效 | 🔶 ohos 硬约束 |
| 12 | 16 KB 页对齐 | Play 上架要求；否则安装/映射失败 | 🔶 nodejs-mobile `d9552e0e01` |

### Phase 1 — 最小可用运行时（MVP）

**目标**：`node-bridge` + `node-runtime` 能在真机上稳定跑起一个**真实服务端**（WebView 加载首屏），并具备最小观测面。

范围：`001-runtime-core` / `002-jni-bootstrap` / `004-payload-bootstrap` / `006-observability`（不含宿主能力桥）。

## 附录 B. 症状 → 处置映射

| 症状 | 最可能原因（层） | 处置 |
|---|---|---|
| `dlopen` 失败 / `dlerror` 为空 | 只从可写目录加载；或 ABI 不匹配（L2） | 库只在 APK 内；确认 `abiFilters`/`splits` |
| Node 起来但 5 ms 内段错误 | `argc` 把尾部 `NULL` 算进去（L3） | §5.10 ②：`argc` 不含哨兵 |
| 首次 V8 堆分配即崩，`si_addr == pc` | `libnode.so` 不是真共享库（ET_EXEC/PIE）（L3） | ELF 门禁① ②；换产物 |
| `Error relocating …: napi_create_function: symbol not found` | addon 缺 `DT_NEEDED libnode.so`（L3） | §4.7；`-l:libnode.so` + `--no-as-needed` |
| 随机 `symbol not found`（多个包都带 C++ 库） | 两份 `libc++_shared.so` 冲突（L2） | P0-5；`-static-libstdc++` |
| `console.log` 全丢 | App 进程 fd1/2 指向 `/dev/null`（L2） | §5.10 ④：重建 pipe + reader 线程 |
| Node 卡住不响应、日志停在某处 | stdout pipe 写满未排空（L2） | 同上；reader 线程必须常驻 |
| 主线程卡死 / ANR | 在主线程做了 `node::Start`/`dlopen`（L1） | §5.10 ③：detached pthread |
| `MODULE_NOT_FOUND`（`requireStack: []`） | 入口路径错 / 解包未完成（L4） | 用绝对路径；先解包再起；读 `.ready-*` marker |
| 解包后文件全在但读不到 | 解包到 `cacheDir` 被清理 / 路径穿越被拒（L2/L4） | 解包到 `filesDir`；看解包统计 |
| `EADDRINUSE` 打崩整个 App | 端口冲突 + 未捕获异常（L4） | §5.10 ⑧⑨：随机端口 + `uncaughtException` 兜底 |
| WebView 白屏但 curl 正常 | cleartext 被禁 / `domStorageAccess` 未开（L1） | §6.3：`networkSecurityConfig` + `setDomStorageEnabled` |
| 状态是 running 但服务不响应 | Node 侧 `process.exit` 让 `node::Start` 返回（L1） | `exited` 态 + 消费方处理 |
| 崩溃无堆栈 | 自建 handler 用了非信号安全函数（L3） | §5.10 ⑤；只 `write(2)`；再用 system tombstone 交叉验证 |
| 安装报 16 KB 页不兼容 | 未加 `max-page-size=16384`（L2） | §5.8 门禁⑧ + `zipalign -P 16` |

## 附录 C. 体积预算

| 项 | 预估值 | 依据 |
|---|---|---|
| `libnode.so`（arm64，未压缩） | **≈100–130 MiB** | ⬜ P0-14；参照 OHOS 24.2.0 arm64 = 120.9 MiB（✅ 锁定记录） |
| `libnode.so`（APK/AAR 内 DEFLATE 后） | ≈35–45 MiB | 同上口径 |
| 引导件 `libnode_bridge.so` | ≈20–40 KiB | 与 OHOS 的 14 KB 同量级 |
| NAPI addon `libnode_host_client.so` | ≈15–30 KiB | 同上 |
| `payload/`（bootstrap+host+selfcheck） | ≈30–50 KiB | OHOS 三件套 1326 行 |
| 库侧增量合计（安装后） | **≈45 MiB** | 压缩后 + 少量描述符 |
| 载荷 | **另一笔账**（消费方） | 与 OHOS 同理 |

> `--with-intl=full-icu`（推荐）比 `--with-intl=none` 多约 20–30 MiB 未压缩（⬜ 实测）；
> 取舍理由：首个消费方载荷依赖 `Intl`（日期/数字格式化），`none` 会让部分 npm 包直接崩。

## 附录 D. 自建 `libnode.so` 配方（Node 24.x，NDK）

```bash
# 0) 前置：Linux 或 WSL2（上游 android_configure.py 只支持 Linux/Darwin）+ NDK r27+ + Python3 + make
git clone --depth 1 --branch v24.x.y https://github.com/nodejs/node node-src
cd node-src

# 1) 打补丁（幂等；每条带 commit 出处）
#    a) V8 trap handler 在 Android 关闭（上游 issue 36287；nodejs-mobile android-patches/trap-handler.h.patch）
#       ⬜ 需在 Node 24 复核：V8 12+ 的 trap-handler.h 已重构，patch 可能需要改写
patch -p0 < ../patches/0001-v8-trap-handler-android.patch

# 2) 配置：上游脚本 + 我们补的两项
export LDFLAGS='-Wl,-z,max-page-size=16384 -Wl,-soname,libnode.so'
./android-configure "$ANDROID_NDK_HOME" 24 arm64        # 上游脚本会跑 ./configure ...
#    ⚠️ 上游脚本**不含 --shared**：等价于手动执行
#    ./configure --dest-cpu=arm64 --dest-os=android --openssl-no-asm --cross-compiling --shared
#      [--with-intl=full-icu]   # 默认即 full-icu；显式写下来便于复现

# 3) 编译
make -j"$(nproc)"

# 4) 取产物 + strip
ls -l out/Release/lib.target/libnode.so out/Release/obj.target/libnode.so
"$ANDROID_NDK_HOME/toolchains/llvm/prebuilt/linux-x86_64/bin/llvm-strip" \
  --strip-unneeded out/Release/lib.target/libnode.so

# 5) 门禁 + 锁
node ../tools/provision.mjs --check --in out/Release/lib.target/libnode.so
```
